# SDD V2 — Engram Canonical-Store Feasibility Audit

## 1. Status

**Frontier 4 — capability audit before adapter implementation**

Target evaluated:

```text
Engram v1.20.0
```

Purpose:

> Determine whether Engram's public MCP/HTTP/store semantics can satisfy the canonical SDD Memory Contract **without** a parallel file store, fuzzy lookup as control state, blind overwrites, or hidden process-local authority.

This is a falsification step, not an adapter implementation.

No conclusion in this document authorizes changing `memory-contract.md` merely to fit Engram.

---

## 2. Inputs

This audit uses the current SDD reconstruction:

```text
docs/rebaseline-architecture.md
docs/memory-contract.md
docs/change-model.md
```

Relevant Memory Contract requirements:

```text
- canonical durable records pass through Memory Contract + adapter
- exact get by id/key
- structured query independent from FTS
- create-if-absent for canonical identity
- optimistic concurrency for mutable canonical records
- append idempotency by SDD record identity
- confirmed writes before success
- no authoritative local side state
- backend restart/new-process recovery
```

Relevant Change requirements:

```text
- CHG identity cannot collide silently
- continuity must recover by exact Change identity
- concurrent updates cannot lose changes silently
- completion against stale state must conflict/re-evaluate
```

Dogfood already established that Engram itself provides real persistence and cross-session survival. This audit therefore focuses on **semantic correctness as a canonical SDD store**, not whether Engram can remember things.

```text
Engram v1.20.0 public surface
```

The failure is not about serialization format.

It is primarily about:

```text

```

## 5. Evidence in Engram implementation

### 5.1 `topic_key` is not create-if-absent

Engram's observation save path does:

```text
if topic_key exists:
  SELECT most recent row with same topic_key + project + scope
  if found:
    UPDATE it
    revision_count++
  else:
    INSERT a new observation
```

For SDD this means:

```text
writer A proposes CHG-...-03
writer B proposes CHG-...-03

desired:
  one created
  one conflict

Engram topic-key behavior:
  create/upsert semantics
```

Even if sequential calls converge on one row, the second caller does not receive the semantic conflict SDD needs to know that the logical identity was already owned.

### 5.2 `topic_key` has an index, not a uniqueness constraint

Engram creates an index equivalent to:

```text
(topic_key, project, scope, updated_at)
```

but not a unique constraint on the logical topic tuple.

Therefore the database itself does not establish the SDD invariant:

```text
one canonical logical key -> one canonical record
```

### 5.3 `revision_count` is not optimistic concurrency

Updates execute by observation ID and increment:

```text
revision_count = revision_count + 1
```

There is no public precondition equivalent to:

```text
WHERE id = ? AND revision_count = expected
```

or:

```text
If-Match: version
```

Thus `revision_count` is useful metadata but not a lost-update guard.

### 5.4 Public exact lookup is backend-ID based

The public exact read is:

```text
GET /observations/{id}
```

The ID is allocated by Engram.

SDD cannot start a new process with:

```text
CHG-20260818-03
```

and directly resolve the canonical observation without already knowing Engram's numeric ID or introducing another lookup mechanism.

### 5.5 Structured canonical query is insufficient

Recent observation listing supports project/scope and bounded recency.

FTS search supports text/type/project filters.

Neither is equivalent to:

```text
query(
  project=...,
  kind=change,
  logical_key=...,
  lifecycle=open
)
```

Serializing SDD markers into `content` and querying those markers through FTS is still FTS-based control state.

## 6. Why the previous Engram adapter spike is insufficient

The previous spike was useful exploration but cannot be used as proof of canonical-store compatibility.

It explicitly states that:

```text
- the real Engram binary was not exercised in the main test
- SDD key/subject lookup used deterministic FTS markers
- that mapping was experimental
```

Its HTTP adapter implements:

```text
get(logical_key)
  -> searchByMarker(...)
  -> FTS
  -> inspect returned records
```

and:

```text
query(kind/subject)
  -> FTS marker search
```

This violates the reconstructed Memory Contract requirement that known workflow state not depend on fuzzy/search ranking.

The old fake also models the API behavior we wished to use, so green tests there cannot establish guarantees absent from the real backend.

The old spike should remain historical evidence, not implementation substrate.

## 7. Rejected compatibility hacks

### 7.1 FTS markers as canonical index

Rejected.

Reason:

```text
known identity -> fuzzy/indexed text search
```

recreates the recovery ambiguity that the reconstruction is intended to remove.

### 7.2 Process-local map: `CHG id -> Engram observation id`

Rejected as authority.

It fails:

```text
restart
new process
new machine
cache deletion
multi-agent
```

A reconstructible cache is allowed only after exact canonical reconstruction is already possible.

### 7.3 `.sdd/state.json` mapping/index

Rejected as canonical support layer.

That recreates the dual-authority problem of `0.2.0-alpha.1`.

### 7.4 Directly depend on Engram's private SQLite schema

Rejected for the product hot path.

It would couple SDD to:

```text
Engram DB path
internal tables
internal migrations
SQLite implementation details
```

and bypass the backend-independent contract.

A diagnostic experiment may inspect the DB, but product correctness must not require private-schema access unless we explicitly choose Engram as a hard dependency and revise the architecture.

### 7.5 Relax create/CAS requirements to fit Engram

Rejected at this stage.

Those requirements exist to solve observed or explicit target risks:

```text
Change identity collision
multi-agent lost update
stale close
multi-worktree/process correctness
```

Removing them would improve adapter convenience while lowering the quality gate we set before dogfood.

## 8. Viable architecture paths

The failed conformance does **not** imply that Engram is poor software.

It means its current public memory semantics and SDD's desired canonical workflow semantics are different.

### Path A — Extend Engram with generic primitives

Add backend-generic memory capabilities such as:

```text
exact get/query by topic_key
unique logical topic constraint or create-if-absent
conditional update by revision/version
caller-visible idempotency key / stable exact sync lookup
structured bounded query fields
```

Important:

These should be generic Engram capabilities, not endpoints named after SDD entities.

Possible result:

```text
SDD Memory Contract
    ↓
thin Engram Adapter
    ↓
Engram public API
    ↓
Engram SQLite
```

Advantages:

- preserves Engram as canonical durable backend;
- no second authoritative store;
- SDD remains backend-independent;
- concurrency semantics live where writes are serialized;
- improvements may benefit other Engram integrations.

Costs/risks:

- requires upstream contribution, fork, or waiting for support;
- deployment/version pin becomes important;
- SDD depends on a minimum Engram capability version.

### Path B — Use a deliberate SDD canonical store; Engram remains semantic memory

Architecture:

```text
SDD Semantic API
  -> SDD Store      canonical workflow state

Engram
  -> semantic/project memory
  -> discovery/history/knowledge where useful
```

This is technically coherent if the SDD Store is intentionally designed.

However it means Engram no longer eliminates SDD's own state store.

That is a major product decision and must not be introduced as a hidden workaround.

### Path C — Change backend

Keep Memory Contract and implement another backend that already supports:

```text
unique keys
CAS/version
structured query
idempotent create
```

Engram could still remain optional semantic memory.

This preserves the architecture but loses Engram as the default canonical store.

### Path D — Weaken the Memory Contract

Not recommended.

It would reproduce known Alpha.1 failure modes and undermine the target quality gate for multi-agent/worktree correctness.

## 9. Preferred next investigation

Because one original V2 objective was to use Engram to avoid rebuilding a file-based workflow store, the next investigation should evaluate **Path A before Path B**.

Question:

> Can Engram expose the missing guarantees as small, generic memory primitives without becoming SDD-specific?

This should be answered before designing another SDD store.

Candidate minimal capability delta to investigate:

```text
1. exact lookup:
   GET observation by project + scope + topic_key

2. atomic create:
   create topic only if absent
   -> created | conflict

3. conditional update:
   update observation expected_revision=N
   -> updated | conflict

4. exact structured list:
   project + scope + type/topic prefix + bounded pagination

5. idempotent append:
   client-supplied idempotency/sync key
```

Do not implement all five yet.

First inspect whether Engram already has internal primitives that can expose them safely with a small public API delta.

```text

```

This is a successful falsification.

```text

```

whose implementation would have required knowingly violating the contract.
